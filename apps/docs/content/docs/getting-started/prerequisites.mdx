Before starting local development, ensure you have all the required tools installed and accounts provisioned.

## Required Tools

| Tool | Required Version | Check Command | Install |
|------|-----------------|---------------|---------|
| **Bun** | 1.2.22+ | `bun --version` | `curl -fsSL https://bun.sh/install \| bash` |
| **Node.js** | 20+ | `node --version` | [nodejs.org](https://nodejs.org) or `brew install node` |
| **Redis** | 7+ | `redis-cli ping` | `brew install redis && brew services start redis` |
| **iii engine** | 0.21.6 (pinned) | `apps/veritio/.iii/bin/iii --version` | Auto-installed on first `dev.sh` run via `apps/veritio/scripts/install-iii.sh` |
| **Git** | any | `git --version` | [git-scm.com](https://git-scm.com) or `brew install git` |

## Required Accounts

- **Supabase** -- You need a Supabase project, either on [supabase.com](https://supabase.com) (cloud) or self-hosted. This provides the PostgreSQL database and storage layer.

## Optional Tools

- **Docker** -- Only needed if you want to run Veritio via Docker Compose instead of natively. See the [Docker Compose](/docs/self-hosting/docker) guide.

## Why Both Bun and Node.js?

Bun is the primary runtime and package manager for Veritio. It handles dependency installation, script execution, and serves as the production runtime for backend step handlers.

Node.js is additionally required because of one specific component: the **Composio trigger listener**. This listener uses `npx tsx` to run, because Bun's WebSocket implementation is incompatible with the `pusher-js` library that Composio uses internally. Without Node.js, the Composio integration (Google Sheets, Slack) will not function, but the rest of Veritio will work fine.

The project pins a specific Bun version in `.bun-version` (currently 1.2.22). If you encounter version mismatch issues, update Bun:

```bash
bun upgrade --stable
```

## The iii Engine

The **iii engine** is a Rust binary that serves as Veritio's backend runtime. Veritio pins engine **v0.21.6**. It provides:

- HTTP routing (all backend step routes on port 4000)
- WebSocket streams (browser stream clients connect to the RBAC listener on port 4004)
- State management (ephemeral key-value store backed by Redis)
- A durable queue (builtin file-based adapter, stored under `./data/queue`)
- Cron scheduling
- Observability (traces, metrics, logs)

The compiled backend app (TypeScript step handlers, registered via the adapter in `src/lib/iii/`) connects to the engine's trusted worker bridge over an internal WebSocket on port 49134.

### Verifying the iii engine

The engine is pinned per checkout under `apps/veritio/.iii/bin/` (gitignored) and installed automatically on the first `dev.sh` run. To install or verify it manually:

```bash
cd apps/veritio
./scripts/install-iii.sh

# Check the pinned binary
.iii/bin/iii --version
# Should print: 0.21.6
```

`scripts/install-iii.sh` downloads the pinned `iii` and `iii-worker` binaries for your platform from the iii GitHub releases. The Docker image pins the same v0.21.6 Linux binaries during build.

### iii Engine Configuration

The engine reads `apps/veritio/config.yaml` (the committed source of truth, using the iii 0.21 `workers:` schema) at startup. Boot scripts seed its `config:` blocks into a `./config/` store on each start. The main workers are:

| Worker | Purpose | Configuration |
|--------|---------|---------------|
| **iii-http** | HTTP server on port 4000 (all step routes) | CORS origins for `localhost:4001` and `localhost:3113` |
| **queue** | Durable queue (builtin file-based adapter) | Stored under `./data/queue`; retries/DLQ/FIFO supported |
| **state** | Ephemeral key-value state across steps | Redis adapter at `REDIS_URL` |
| **iii-stream** | Stream storage/pub-sub (internal worker on 4014) | Redis adapter at `REDIS_URL` |
| **iii-worker-manager** | Browser stream RBAC listener on port 4004 | Trusted worker bridge on 49134 (loopback only) |
