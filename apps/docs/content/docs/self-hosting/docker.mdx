Docker Compose runs the Veritio application services. It does **not** provision Supabase or deploy the optional Cloudflare live-test worker, so it is not a complete one-command infrastructure stack.

## Quick Start

```bash
# 1. Copy and configure environment variables
cp .env.example .env
# Replace every required placeholder; generate each secret independently:
# openssl rand -hex 32

# 2. Bootstrap the external Supabase database through its direct/session URL
cd apps/veritio
DATABASE_DIRECT_URL='postgresql://...' bun run self-host:migrate
cd ../..

# 3. Build and start the application services
docker compose up -d --build

# 4. Wait for redis, backend, yjs, and frontend to report healthy
docker compose ps
```

## Services

Docker Compose runs four services:

| Service      | Image                            | Port       | Dependencies              |
| ------------ | -------------------------------- | ---------- | ------------------------- |
| **redis**    | `redis:7-alpine`                 | 6379       | None                      |
| **backend**  | Built from `Dockerfile`          | 4000, 4004 | Redis (healthy)           |
| **frontend** | Built from `Dockerfile.frontend` | 4001       | Backend and Yjs (healthy) |
| **yjs**      | Built from `Dockerfile.yjs`      | 4002       | Redis (healthy)           |

**Important:** Supabase is **not** included in the Docker Compose setup. You still need an external Supabase instance (either cloud-hosted at [supabase.com](https://supabase.com) or self-hosted separately) for PostgreSQL and storage.

The **backend** service mounts a named volume (`backend-queue` -> `/app/apps/veritio/data`) for the durable queue and state file stores, so both survive restarts and redeploys.

## Docker Image Details

### Backend Dockerfile (Multi-Stage)

The backend Dockerfile uses a multi-stage build:

1. **Builder stage** -- Downloads the `iii` and `iii-worker` v0.23.0 Linux archives from the [iii GitHub releases](https://github.com/iii-hq/iii/releases) and verifies committed SHA-256 digests
2. **Runtime stage** -- Uses `oven/bun:1.3-slim`, installs dependencies, prefetches the exact registry packages in `worker-compose.yaml`, then bundles the backend as `dist/backend.mjs`
3. **Start** -- The `start.sh` entrypoint starts the managed iii Compose topology, waits for the trusted bridge, then runs `dist/backend.mjs`

### Frontend Dockerfile (Multi-Stage)

1. **Builder stage** -- Runs a full monorepo `bun install`, then builds the Next.js production bundle with `bun run build`
2. **Runtime stage** -- Copies the `.next` output directory and serves it with `bun run start`

### Yjs Dockerfile (Single-Stage)

A single-stage build that runs `bun run server.ts` to start the Yjs WebSocket server.

## Environment Variables

You must set all required environment variables in your `.env` file before starting Docker Compose. At minimum:

| Variable                        | Description                                                                           |
| ------------------------------- | ------------------------------------------------------------------------------------- |
| `NEXT_PUBLIC_SUPABASE_URL`      | Your Supabase project URL                                                             |
| `SUPABASE_INTERNAL_URL`         | Optional server-only origin when Docker reaches Supabase through a different hostname |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Supabase anonymous key                                                                |
| `SUPABASE_SERVICE_ROLE_KEY`     | Supabase service role key                                                             |
| `DATABASE_URL`                  | PostgreSQL runtime connection (transaction pooler)                                    |
| `DATABASE_DIRECT_URL`           | Direct/session PostgreSQL URL used from the host for migrations and backups           |
| `BETTER_AUTH_SECRET`            | Session signing secret (32+ chars)                                                    |
| `BETTER_AUTH_URL`               | Your deployed frontend URL                                                            |
| `BETTER_AUTH_COOKIE_DOMAIN`     | Optional shared cookie domain; leave unset for localhost or a single host             |
| `NEXT_PUBLIC_APP_URL`           | Your deployed frontend URL                                                            |
| `REDIS_PASSWORD`                | Generated Redis password; no shared Compose default exists                            |
| `YJS_INTERNAL_API_KEY`          | Independent generated key for backend-to-Yjs requests                                 |

Compose constructs the internal authenticated `REDIS_URL`; do not put a second conflicting value in the Compose service definition. `NEXT_PUBLIC_*` values are compiled into the frontend image, so changing a public URL requires `docker compose build frontend` before restart.

See the full [Environment Variables](/docs/getting-started/environment-variables) reference for all available configuration options.

## Managing the Deployment

### View Logs

```bash
# All services
docker compose logs -f

# Single service
docker compose logs -f backend
docker compose logs -f frontend
```

### Restart a Service

```bash
docker compose restart backend
```

### Stop All Services

```bash
docker compose down
```

### Updating

Pin deployments to a released tag. To update, read its release notes, back up Supabase and the named Docker volumes, then:

```bash
git fetch --tags
git checkout vX.Y.Z
cd apps/veritio
DATABASE_DIRECT_URL='postgresql://...' bun run self-host:migrate
cd ../..
docker compose up -d --build
docker compose ps
```

Do not deploy an arbitrary moving `main` revision in production. See the [operations runbook](https://github.com/Ankish8/Veritio/blob/main/docs/SELF_HOSTING_OPERATIONS.md) for backup and rollback boundaries.

## Health Checks

The backend service includes health checks that Docker Compose uses to determine when it is ready. The frontend service depends on the backend being healthy before it starts.

You can verify services are running:

```bash
# Backend API
curl -s -o /dev/null -w "%{http_code}" http://localhost:4000/api/health

# Frontend liveness and readiness
curl --fail http://localhost:4001/health/live
curl --fail http://localhost:4001/health/ready

# Yjs liveness and readiness
curl --fail http://localhost:4002/health/live
curl --fail http://localhost:4002/health/ready

# Browser stream listener (a successful TCP connection is sufficient)
nc -z localhost 4004

# Redis
docker compose exec redis sh -c 'redis-cli -a "$REDIS_PASSWORD" ping'
```

If live website tests are enabled, also require HTTP 200 from the worker's `/health/ready` endpoint. A plain `/health/live` only proves the worker isolate can execute; readiness additionally checks required configuration and backend reachability.
